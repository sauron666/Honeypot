# 03 — Honeytokens

Примамка без инфраструктура: стойност, която нищо легитимно не докосва, затова
всяко нейно използване е сигнал. MIRAGE има 8 типа и следи за тях по два начина
— когато атакуващият **набере** callback URL-а, и когато подхвърлената стойност
**се появи** някъде (watcher).

## От конзолата (GUI)

1. Отвори **Honeytokens** секцията.
2. Избери тип (URL, AWS ключ, API токен, DB connection string, SSH ключ,
   credential, .docx…), дай етикет и къде ще го подхвърлиш.
3. Натисни **mint**. Токенът се появява в списъка.
4. За `office-doc` тип натисни **docx** — сваля .docx, който звъни вкъщи, щом го
   отворят.

## От CLI

Командата говори с живия директор през API-то (`-api`, `-token` при нужда).

```bash
# издай URL токен
./bin/miragectl tokens -mint url -label "finance share" -location "\\\\fs01\\finance"

# виж всички (без -mint/-delete просто ги изрежда)
./bin/miragectl tokens

# издай .docx примамка
./bin/miragectl tokens -mint office-doc -label "Q4 board deck"

# изтрий токен
./bin/miragectl tokens -delete <token-id>
```

## Как гърми

- **Callback**: AWS ключ, API токен, URL — щом атакуващият ги пробва срещу декой
  или набере URL-а, токенът гърми при **critical** severity, с етикета, който му
  даде („това е ключът от finance share").
- **Observed value** (watcher-ът): подхвърлената парола/стойност се появи в нещо,
  което атакуващият прави на декой (напр. mysql login с тази парола) → свързва се
  автоматично.

Пример на живо: подхвърли парола-токен, после я използвай срещу mysql декоя —
конзолата показва токена като задействан и го връзва към engagement-а.

## Къде да ги подхвърлиш

Honeytokens нямат стойност, докато не са там, където атакуващият гледа:
- във файлов дял (виж [Breadcrumbs](09-breadcrumbs.md) — автоматизира го),
- в .env / config файл,
- в password мениджър export,
- в имейл/wiki като „временни креденшъли".

## Съвет

Дръж `alerts.min_severity: high` — deception обещава малко аларми, всичките
реални. Токен, който гърми, е винаги реален сигнал.
